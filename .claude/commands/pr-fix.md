# PR Fix — CI レビュー指摘のトリアージ & 修正

CI の自動レビュー（Claude Code Review など）の指摘を読み、プロジェクト文脈を踏まえて判断・修正する。

**Input**: PR 番号（省略時は現在のブランチの PR を自動検出）

## Steps

### 1. PR を特定する

```bash
gh pr view --json number,title,headRefName --jq '.number'
```

引数で PR 番号が渡された場合はそれを使う。
PR が見つからない場合はエラーを出して終了。

### 2. レビューコメントを取得する

GitHub MCP の `pull_request_read` (method: `get_comments`) でコメントを取得。
bot によるレビューコメントのみを対象にする（人間のコメントはスキップ）。

コメントが見つからない場合は「レビューコメントがありません」と表示して終了。

### 3. 指摘を構造化する

各指摘について以下を抽出:
- **タイトル**: 指摘の要約
- **重要度**: Critical / High / Medium / Minor（レビュアーの評価）
- **対象ファイル・行**: コードの場所
- **問題の説明**: 何が問題か

### 4. プロジェクト文脈を収集する

判断に必要な文脈を読む:
- **GitHub Issues**: `gh issue list` で関連する既存 Issue を確認
- **OpenSpec**: `openspec/specs/` から関連するスペックを確認
- **CLAUDE.md**: プロジェクトの方針・フェーズを確認
- **Memory**: auto memory から関連するメモを確認

### 5. 各指摘をトリアージする

各指摘に対して、文脈を踏まえて以下のいずれかを判断:

**FIX（今修正する）**:
- コードの明確なバグ
- パフォーマンス改善（簡単にできるもの）
- 型安全性の向上
- 不要なコードの削除
- テストの修正

**DEFER（Issue に回す）**:
- 既存の Issue で対応予定のもの
- スコープ外の大きなリファクタリング
- アーキテクチャの変更が必要なもの
- 別の feature ブランチで対応すべきもの

**SKIP（対応不要）**:
- 現在のフェーズでは該当しない指摘（例: Phase 2 のネットワーク問題）
- 技術的制約による仕様（例: E2E/Vite 境界の型重複）
- レビュアーが文脈を知らないために出た誤指摘
- 既に意図的にそうしているもの

### 6. トリアージ結果を表示し、即座に実行する

全指摘のトリアージ結果を表形式で表示:

```
| # | 指摘 | 重要度 | 判断 | 理由 |
|---|------|--------|------|------|
| 1 | Tower projectiles... | High | DEFER | #94 Entity一般化で解消 |
| 2 | Definition duplication | Medium | FIX | 簡単に修正可能 |
| 3 | Math.sqrt perf | Medium | FIX | ホットパスの最適化 |
```

**確認を待たずに次のステップへ進む**（自律判断モード）。

### 7. FIX の修正を実装する

FIX と判断した指摘を順に修正:
- コード変更は最小限に
- 各修正後にテストが通ることを確認（全修正後にまとめて実行でも可）

### 8. テスト実行

```bash
npm run test:unit
npx playwright test
```

全テストがパスすることを確認。失敗した場合は修正。

### 9. コミット & プッシュ

修正をまとめて1コミットで作成:
```
fix: address PR review feedback

- [FIX した内容の箇条書き]
```

### 10. PR にトリアージ結果を返信する

GitHub MCP の `add_issue_comment` で PR にコメントを投稿:

```markdown
## Review Triage

### Fixed
- [修正した指摘のリスト + 何をしたか]

### Deferred
- [Issue に回した指摘 + 理由 + Issue リンク]

### Skipped
- [対応不要の指摘 + 理由]
```

## Guardrails

- トリアージは自律判断で実行する（ユーザー確認不要）
- DEFER の場合、既存 Issue がなければ新規 Issue を自動作成する
- セキュリティ関連の指摘は原則 FIX（SKIP しない）
- 修正は最小限に — レビュー指摘の範囲を超えた変更をしない
- テストが通らない修正はプッシュしない
